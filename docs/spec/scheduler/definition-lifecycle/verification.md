## 条件と検証範囲

Linux 6.18 x86_64、.NET SDK 10.0.403、Node 24.22.1、Azurite 3.35.0、Chromium 155.0.8059.79。cgroup上限はCPU 4コア相当、メモリ16GiB。実行器はRelease、CIのNodeは22。専用AzuriteでTable/Blob、実HTTP、実プロセス、ブラウザーを確認する。実Azure、実JP1、Windows実行器は未検証。

- 通常起動は保存済み定義を復元し、入力Blob変更や消失に左右されない。定義未登録状態から明示反映でき、停止を維持する。設定不一致や破損を空状態で上書きしない。
- 停止中に起動済みプロセスを回収でき、新規開始はしない。再起動をまたぐ停止、再開時の保留済み過去ルート見送り、開始済みネットの後続再開、古い停止版の競合を確認する。
- 通常未来予定の置換、旧定義へ固定した個別操作・取消・開始済み世代、切戻しと再起動での非重複を、件数/日数の両方式で確認する。明示の期間・固定日時・間隔・初回保留、削除ルートの旧世代の完了も確認する。
- 反映計画の参照直後、99行の途中バッチ、最後のバッチ、適用完了印、ルートのみ、子の途中、Materialized印保存前で中断する14通りを確認する。世代途中は先読み期間を超える10日停止後にも同じID/実行IDで復旧し、過去の再実行を起こさない。
- 旧形式1〜5から採用IDと世代IDを維持して6へ移行する。旧監視上書きと受付済み登録の版を固定し、初回保留の消化後に再反映しても後続へ保留を拡散しない。
- 共有下書きは無効な編集値の保存、2クライアントのCAS競合、同じ保存の応答喪失後の再送、再読込中の編集保護を確認する。運用反映の版・対象状態・予定時刻経過の競合を確認する。
- 複数ノード/子孫/内部接続のコピー、外部接続の除外、別ファイル・文字コード・名前衝突・未編集原文・undo/redo・保存復元を確認する。月表示の閏日・親継承・jc参照・個別指定解除は実行エンジンと照合する。

## 制限

- 全API/実行器を停止して保存形式6へ移行する。旧バイナリとのローリング更新はしない。
- 共有下書きはSchedulerIdにつき1件。一式置換のため、古い基点と現在の定義の自動マージはしない。
- 部分反映中の読取は再取得を求め、新規開始も待機する。反映時間は世代数・子の数とStorageの応答に依存する。
- HTTP本文12MiBは原文のサイズ制限とは別に適用する。コピー履歴のスナップショットや基点を含む大きな下書きはこの上限に達する場合がある。
- 切り取り、階層の役割変更を伴う貼付、別ブラウザーへのコピー、別形式Calendar/Schedule、認証、計画実行登録は対象外。

## PR #8 の追加レビュー対応

基点 `1d5e700`。`main` の [CI](https://github.com/akrym1582/JobRunner/actions/runs/42306001155) では `groups.spec.ts` の削除→undo→redo→再読込後にネット数が1ではなく2になっていた。IndexedDBの比較用get成功後、put前でトランザクションを保ったまま待機させ、redo直後の表示を検査したところ、削除後の画面に古い「保存済み」が残ることを再現した。保存状態は文字列だけで保持せず、保存が完了した基点と編集履歴の組から描画する。再度のundo/redoと先行保存待ち、保存完了後の再読込でも削除が維持されることを検証した。

## 原文マッピングの追加確認
