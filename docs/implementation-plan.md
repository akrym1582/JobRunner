# JobRunner 実装計画

- 対象リポジトリ: https://github.com/akrym1582/JobRunner
- 作成日: 2026-11-05
- 状態: 実装前の計画案。ユーザーと確認した要件、設計上の提案、未確定事項を区別する。
- 想定配置先: リポジトリの `docs/implementation-plan.md`

## 1. 目的

JP1/AJS3 Version 12のユニット定義およびカレンダー定義を取り込み、スケジュールに沿って同一マシン上のジョブを実行する、Web API専用のジョブスケジューラーを実装する。

画面、API認証、リモートジョブ実行を持たず、JP1 V12のスケジュール計算、実行登録、世代管理、実行制御と、対応するWeb APIの互換性に重点を置く。

本プロジェクトは非公式の独立実装である。JP1全体との完全互換を宣言せず、仕様確認とテストで検証した範囲を公開する。段階的な実装は行うが、最終目標を単純なcron相当へ縮小しない。

## 5. JP1 V12互換方針

### 5.1 仕様対応表

実装前に `docs/compatibility-v12.md` を作成する。各項目について、公式資料の版・章節、入力パラメーター、評価規則、例外、対応状態、テストID、実機比較の有無を記録する。

対応状態は「調査中」「未実装」「実装済み・仕様テスト済み」「JP1比較済み」「対象外」に分ける。「実装済み」と「互換確認済み」を混同しない。

### 5.2 スケジュールの目標範囲

| カテゴリ | 調査・実装対象 |
| --- | --- |
| カレンダー | 稼働日・休業日、上位からの継承、他カレンダー参照、例外日 |
| 実行日 | 日次・週次・月次・月末・営業日基準、開始日・終了日 |
| 振り替え | 前後への振り替え、許容範囲、月境界、実行しない条件 |
| 時刻 | 開始時刻、日付切り替え、業務日、日またぎ、対応する時刻間隔指定 |
| 複数ルール | 同一ジョブネットの複数ルール、同一日時の扱い |
| 階層 | ルート・ネストジョブネット、上位と下位のスケジュール関係 |
| 実行登録 | 計画・確定・即時、登録期間、世代生成と保持 |
| 一時変更 | 日時変更、即時化、実行中止、変更解除 |
| 実行制御 | 多重起動、保留、先行・後続、条件分岐、待ち合わせ |
| 異常・運用 | 正常・警告・異常、異常時後続、再実行、中断、強制終了 |

これは最終的な調査・実装目標であり、上表のすべての詳細仕様を確認済みという意味ではない。細かな名称やパラメーターはV12資料で確定する。

cronへの一律変換は行わない。JP1の意味を保持した内部モデルで評価する。実行日、業務日、実時刻、ルール識別子を分けて保持する。

### 5.3 定義インポート

1. 原文、明示された文字コード、ハッシュを保存する。
2. 字句解析と構文解析で階層・文字列・繰り返し属性を読み取る。正規表現の単純な分割だけで済ませない。
3. カレンダーがユニット定義に含まれる場合は共通パーサーを使用する。別形式は確認後に入力アダプターを追加する。
4. 未知属性、循環参照、接続不整合、カレンダー参照不足、実行先属性を検証する。
5. 実行に影響する未対応属性を含む定義は有効化不可とする。表示位置等の無害な属性は保存し、無視した旨を返す。
6. 定義・カレンダー一式を不変のバージョンとして保存し、有効版への参照を切り替える。

内部処理ではインポートと実行登録を分離する。起動時の自動初期化では、検証・版保存・確定実行登録を一連の処理として行い、完了後に実行可能とする。管理APIによる単独インポートは登録を伴わない。Shift_JIS等の対応文字コードは実データで検証し、自動推定だけに依存しない。

## 6. 永続データとメモリ

### 6.1 Blob Storage

| パス例 | 内容 |
| --- | --- |
| locks/{schedulerId}/leader | 稼働系選出用の専用Blob |
| definitions/{versionId}/source.txt | 取り込み原文 |
| definitions/{versionId}/model.json | 正規化した定義・カレンダーと形式バージョン |
| definitions/{versionId}/manifest.json | 原文ハッシュ、文字コード、対象版、検証結果 |
| logs/{executionId}/{attemptId}/... | 標準出力・標準エラー等 |

定義Blobは不変とし、全ファイルの保存成功後にTable上の有効版を更新する。BlobとTableを跨ぐ原子トランザクションはないため、孤立した未参照Blobは後で回収する。メモリの全状態を定期保存するだけの方式にはしない。

### 6.2 Table Storage

初期案では、1つの制御用Tableに、スケジューラー単位のPartitionKeyを設ける。同一パーティションで稼働系の管理行とジョブ状態を同時更新できることを優先する。1日1,000件でも保持期間とピーク負荷を測定する。

| RowKey例 | 内容 |
| --- | --- |
| leader | OwnerInstanceId、Epoch、ETag、状態 |
| definition-active | 有効ハッシュ、stateNamespace、初期化状態への参照 |
| registration:{id} | 実行登録種別、対象、期間、登録版 |
| occurrence:{stateNamespace}:{sortTime}:{id} | 予定日時、業務日、ルール、世代、定義版、状態 |
| attempt:{stateNamespace}:{executionId}:{attemptId} | 起動試行、所有者、Epoch、PID補助情報、終了結果 |
| command:{requestId} | 操作要求、対象、要求ハッシュ、処理結果 |
| override:{id} | 世代単位の一時変更と解除情報 |

キーはパスを直接連結せず、禁止文字を考慮した安定エンコードまたはハッシュを使う。予定IDは登録ID・ルール・業務日等から決定的に生成し、同一時刻でもJP1上別世代となるケースを誤って統合しない。

ETagによる条件付き更新を必須とし、競合時にワイルドカードで強制上書きしない。同一パーティションのトランザクション上限は100操作・4MiBを前提に検証し、巨大なジョブネットは小さな再開可能処理へ分割する。

終了済み履歴は保持期間に応じて日付別の履歴へ退避できる設計とする。退避はコピーの成功確認後に元を消し、途中障害でも欠落しない。初版から複雑な分散インデックスを作らない。

### 6.3 メモリ

解析済み定義、評価済みカレンダー、直近の予定キュー、実行中プロセスへの参照を保持する。永続化した状態から予定・依存関係を復元できるようにする。重要な状態変更は永続化後にメモリへ反映する。

## 7. 稼働系・待機系と排他

### 7.1 リースの基本案

- リース期間60秒、更新間隔15秒、待機系の取得間隔5〜10秒＋ジッターを初期案とする。
- 無期限リースを使用しない。
- 更新処理をジョブ実行や重い予定計算と分離する。
- 成功を確認できたリース取得・更新と単調時計を使い、余裕を持ったローカル有効期限を管理する。
- 更新失敗・有効期限不明時は直ちに新規起動を止める。SDKの再試行が期限を超えて継続しないよう制限する。
- 有効期限を過ぎたインスタンスは復帰時も稼働系として動かず、選出からやり直す。

### 7.2 Tableへの古い書き込みを防ぐ

BlobリースはTableやOSプロセスを保護しない。追加の世代管理が必要である。

1. Blobリース取得後、Tableのleader行をETag条件付きで更新し、新しいEpochを発行する。
2. リースの有効性と、Tableの所有者・Epochが自分に一致することを確認して初めて起動可能状態へ移る。
3. 状態更新は、現在のleader行へのETag条件付き更新と対象行の変更を、同一Table・同一パーティションのトランザクションで行う。
4. 古いEpochの処理は、新しいleaderのETagを取得して書き込みを続けてはならない。所有者・Epoch不一致で終了する。
5. 稼働系内の状態変更は一本のコマンド処理経路へ集約し、競合を減らす。

Blob取得とTableの世代更新も原子的ではない。取得途中の停止、応答遅延、期限切れ直後の復帰を含むプロトコル試験を行う。世代番号は古い状態更新の拒否に使えるが、すでに開始した外部プロセスを止める保証にはならない。

### 7.3 プロセス起動と保証の限界

起動前にStartingとattemptIdを永続化し、リースを再確認してプロセスを起動し、成功後にRunningを記録する。DB更新とProcess.Startは原子的ではなく、確認直後の停止やネットワーク分断を完全には排除できない。

したがって、業務処理のexactly-onceを保証しない。新稼働系は旧稼働系のStarting/Runningを自動再起動せず、結果不明として扱う。外部業務の二重更新を厳密に防ぐ必要があるジョブには、実行IDによる冪等性または実行先での排他が必要である。

リース喪失時はプロセスツリーの停止を試みるが、OSやジョブの挙動によって停止できない場合や、すでに副作用が発生した場合がある。新稼働系はそれを成功・失敗と推測しない。

### 7.4 復旧時の扱い

| 状態 | 方針 |
| --- | --- |
| 未開始の予定 | 保存状態を復元し、復旧基準時刻より前の未開始ルート世代はスキップ。未来の予定から再開 |
| 旧所有者のStarting/Running | 結果不明。自動再実行しない |
| 完了結果保存済み | 保存結果から後続の可否を再評価 |
| 結果不明に依存する後続 | 待機を維持 |
| 未処理のAPI操作 | 同じrequestIdで重複なく再開 |
| 途中の予定生成 | 決定的なキーとチェックポイントで再開 |

結果不明の世代と多重起動禁止が関係する後続世代も、安易に起動しない。無関係なジョブネットは継続可能とする。手動解決は理由、対象attemptId、期待状態を必須にし、履歴へ残す。

## 8. スケジュール計算と世代管理

ScheduleCalculatorは、定義版、カレンダー、登録条件、期間、タイムゾーンを受け取り、予定と計算根拠を返す。StorageやProcessへ直接アクセスしない。

- UTCの実時刻、ローカル表現、業務日を分ける。
- 日付切り替え前後、月末、うるう年、参照カレンダーの境界を明示的に評価する。
- 予定生成は一定期間を先読みし、範囲カーソルから補充する。
- 同時刻に複数ルールが一致した場合の世代数は、JP1の仕様で決める。
- 登録時の定義、実行時に固定する定義、一時変更を分ける。変更をどこまで反映するかは登録種別ごとに確認する。
- 実行中の世代へ新しい定義を混入させない。
- カレンダー変更で全未開始世代を一律再計算しない。確定実行、一時変更済み等の意味を保持する。
- 保存されたタイマーの発火回数ではなく、永続化された世代を基準に実行する。

内部状態例はPlanned、Waiting、Held、Starting、Running、Succeeded、Warning、Failed、Cancelled、Unknownとする。これは独自内部モデルであり、JP1の状態コードへの変換表は別途定義する。

## 9. ローカル実行

- 引数、作業ディレクトリ、環境変数、終了判定を定義から組み立てる。
- 実行ファイルとシェル実行を区別する。引用符・引数の仕様をOS別にテストする。
- 標準出力と標準エラーを並行して読み、出力詰まりによる停止を防ぐ。
- ログはメモリ無制限蓄積を避け、分割してBlobへ送る。未送信分は障害で失われ得るため欠落を表示する。
- 最大同時実行数を設定可能にする。初期値は低めに置き、集中時の負荷で調整する。
- 成功、警告、異常、タイムアウト、停止を区別する。
- 再実行は新しいattemptIdを発行し、過去の結果を上書きしない。
- すべてのインスタンスに同一のジョブ資産と環境を配備する。ローカル生成ファイルを別インスタンスへ引き継げるとは仮定しない。
- OSユーザー切り替え等の未対応属性も検証対象にする。

## 10. Web API

### 10.1 JP1互換API

URL、HTTPメソッド、パラメーター、日時形式、状態コード、エラー、登録・操作後の状態遷移をV12公式リファレンスから確定する。推測でJP1風のAPIを作成しない。

対象候補はユニット一覧・詳細、実行結果、計画・確定・即時実行登録、解除、保留変更、計画一時変更、中断、強制終了、再実行、待ち合わせ操作等とする。使用APIだけに最終範囲を固定せず、対応表に沿って拡充する。

認証とエージェント管理は明示的な互換対象外。認証フローを必須とする既存クライアントまで無変更動作を保証しない。

### 10.2 独自管理API案

以下のパスはJobRunner独自案であり、JP1公式APIのパスではない。

| メソッド・パス | 用途 |
| --- | --- |
| POST /api/jobrunner/definitions/validate | 有効化せず取り込み検証 |
| POST /api/jobrunner/definitions/import | 不変の定義・カレンダー版を保存 |
| POST /api/jobrunner/definitions/{version}/activate | 有効版切り替え要求 |
| POST /api/jobrunner/schedules/preview | 指定期間の予定と根拠を取得 |
| GET /api/jobrunner/operations/{requestId} | 操作結果照会 |
| GET /api/jobrunner/executions/{id}/logs | ログ照会 |
| POST /api/jobrunner/executions/{id}/resolve | 結果不明の明示的解決 |
| GET /api/jobrunner/compatibility | 対応機能・未対応機能 |
| GET /api/jobrunner/status | 稼働系、待機系、Epoch、復旧状態 |
| GET /health/live | プロセス稼働確認 |
| GET /health/ready | API受付に必要なStorage等の状態確認 |

変更操作は任意インスタンスで要求をTableへ保存し、稼働系が適用する。同一requestId・同一内容は同じ結果を返し、同一IDで内容が異なる要求は拒否する。適用結果とコマンド完了を可能な範囲で同一トランザクションに入れる。

独自APIでは202と操作IDを利用できる。JP1互換APIには独自の202応答を一律に導入せず、公式の同期・非同期・タイムアウトの意味に合わせる。HTTPタイムアウトを操作未実行と誤認しない仕組みを設ける。

## 12. 検証計画

### xUnitとCI

- ユニット・結合・互換性のテストをxUnitで実装する。仕様ごとの単一ケースはFact、日付境界やルールの組み合わせはTheory等で整理する。
- xUnitおよびテストランナーのバージョンは実装時に.NET 10との適合を確認して固定し、CIでテスト検出数も確認する。0件での成功を完了としない。
- TimeProviderとテスト用実行器・Storage代替を利用し、長い実時間待機や本番ジョブ起動なしで状態遷移を検証する。
- Storageを使う結合・統合テストはAzuriteを必須環境として実行する。実Azureでの検証は今回の完了条件に含めず、資格情報を要求して作業を止めない。
- Release構成でソリューション全体をビルドし、xUnitテストを実行する。StyleCopの解析はテストコードにも適用する。
- 本体・テストの両方でXMLドキュメント生成とビルド時解析を有効にし、警告をエラーとして扱う。CIでも解析を無効にせず、許可した抑制以外の警告・エラー0件を必須にする。
- テストのコメントにも、検証する業務ルールと、その境界条件が重要な理由を日本語で記載する。

### Azuriteを使うローカル・CI検証

- Azuriteのバージョンを固定し、BlobとTableの両サービスを起動する。起動方法、エンドポイント、テスト用接続設定をリポジトリに記載する。
- 開発環境に合わせてコンテナーまたはnpm等で起動できる手順を用意する。アプリ本体は.NETのみとし、Azurite用の実行環境を本体の実行依存に混入させない。
- CIはAzuriteの起動と応答確認後にxUnitを実行する。未起動・接続不能時は必須テストをスキップせず、環境起動を修復するか明確な失敗として扱う。
- 本番と同じAzure SDKとStorageアダプターを使用し、テスト設定で接続先だけを切り替える。Azuriteテストをインメモリ代替だけで済ませない。
- テストごとにコンテナー名・テーブル名・スケジューラーIDを分離する。同じ競合シナリオに参加する複数インスタンスだけが同じ名前空間を共有する。
- 再起動・フェイルオーバー試験中はAzuriteのデータを保持し、アプリのメモリ消失から復元できることを確認する。後片付けは試験完了後に行う。
- ネットワーク分断、応答喪失、更新遅延等は、制御可能な通信経路や障害注入を併用して再現する。疑似障害だけで検証した項目とAzurite上で実際に確認した項目を区別する。
- 採用版AzuriteとSDKの互換性を確認する。未対応APIを避けるために本番コードの排他や整合性確認を無効化しない。
- 実Azure固有のサービス差異、認証、ネットワーク構成、本番性能は今回の検証保証範囲外として記載する。将来の追加検証候補であり、今回の実装完了を待たせる必須作業にはしない。

### StyleCop.Analyzersとコメント品質

StyleCop.Analyzersを開発初期から本体・テストへ導入する。最後に大量の指摘をまとめて修正する運用にしない。パッケージはバージョンを固定し、PrivateAssetsを設定する。

csprojに追加してよい警告抑制は、次の設定のみとする。

```xml
<PropertyGroup>
  <GenerateDocumentationFile>true</GenerateDocumentationFile>
  <RunAnalyzersDuringBuild>true</RunAnalyzersDuringBuild>
  <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  <NoWarn>$(NoWarn);SA1101;SA1200;SA1309;SA1629;SA1633</NoWarn>
</PropertyGroup>
```

- 上記以外の発生するStyleCop警告・エラーは、ソースとコメントを修正してすべて解消する。
- NoWarnの追加、pragma、SuppressMessage、.editorconfigのseverity=none/silent、解析除外、手書きコードの生成コード扱いなどで指摘を回避しない。
- CS1591等のXMLコメントに関するコンパイラー警告も抑制しない。既定テンプレートや共通設定に追加の抑制がないことも確認する。
- XMLコメントは型、コンストラクター、プロパティ、メソッド、列挙値などに必要な説明を記載する。公開APIだけでなく、内部実装の理解に必要な説明も省略しない。
- summaryでは「何をするか」に加え、「何のために必要か」を説明する。識別子を日本語に言い換えただけの文や、同じ定型文の繰り返しで埋めない。
- paramでは引数の意味、単位、タイムゾーン、有効範囲、nullや空値の意味など、該当する契約を説明する。
- returnsでは結果の意味、空・false・nullとなる条件、利用側で必要な扱いを説明する。
- exceptionやremarksでは、実際に存在する例外条件、副作用、前提、並行実行、再試行、キャンセルの意味などを必要に応じて説明する。存在しない保証は書かない。
- 本文コメントは、判断の理由、JP1の業務用語、状態遷移、排他・障害復旧の注意点を解説する。「変数に代入する」「ループする」「保存メソッドを呼ぶ」など、実装の逐語的な説明を追加しない。
- inheritdocの乱用で固有の説明を省略しない。契約の継承だけで十分な箇所に限定し、実装固有の注意は別途説明する。
- 日本語の説明とStyleCopの定型表現が衝突する場合は、まず採用版のstylecop.jsonで利用できる文書化設定を確認し、日本語の説明を保ったまま診断にも適合させる。抑制を追加して解決しない。
- 説明の具体性、正しさ、初心者への分かりやすさは静的解析だけでは確認できないため、人が読む前提のレビュー項目にする。

コメント例（意図を示す抜粋。実際の宣言に必要なparam等は別途記載する）:

```csharp
/// <summary>
/// 指定した業務日の実行予定を、休業日の振り替え規則も含めて算出します。
/// 業務日は午前0時で区切る日付とは限らないため、定義された日付切り替え時刻を使って判定します。
/// </summary>
/// <remarks>
/// この処理は予定の確認にも使います。算出した予定を保存したり、ジョブを起動したりはしません。
/// </remarks>
```

本文コメントの例:

```csharp
// 旧インスタンスで業務処理だけが完了している可能性があるため、結果不明のジョブは再起動しません。
// 自動でやり直すと同じ更新を二度行うおそれがあるので、APIから結果を確定するまで後続も待機させます。
```

### スケジュール互換

- 月末、年末、2月29日、休日連続、前後振り替え、月を跨ぐ振り替え。
- 日付切り替え直前・直後、業務日と実日付の違い。
- 継承・参照カレンダー、複数ルール、ネストの組み合わせ。
- 計画・確定・即時、日時変更、中止、解除、定義変更。
- 少なくとも1年分と、うるう年を含む追加期間の予定を比較する。
- 期待値には公式資料の根拠またはJP1実出力を紐付ける。実装自身から期待値を生成しない。

### 障害・排他

- 2台同時起動、リース取得競合、更新失敗、長時間停止後の復帰。
- Blob到達不能だがTable到達可能、その逆、応答だけが失われたケース。
- Starting保存直後、プロセス起動直後、完了保存直前での強制停止。
- Epoch更新途中、操作適用直後、Blob保存後の有効化前での停止。
- 旧Epochの更新拒否、同一予定の重複開始権取得拒否。
- 結果不明の実行と関連する後続を自動起動しないこと。

### 規模・運用

- 1日1,000ジョブの通常分布と集中分布を検証する。
- 1,000件がジョブネット数か末端ジョブ数かを記録する。未確定の間は末端ジョブ1,000件/日を暫定基準とする。
- 開始遅延、予定計算時間、Storage要求数、競合率、メモリ、ログ量を測定する。
- 遅延許容値は計測後に決定し、秒単位の正確な開始を未検証で保証しない。
- Azuriteでリース・ETag・同一パーティションのトランザクション動作を検証する。採用バージョンで再現できないサービス挙動は明記し、疑似障害テストでアプリ側の判断を補完する。実Azureの挙動まで確認したとは記載しない。
- 外部コマンドの試験には安全な専用フィクスチャを使う。

### 14.1 Codexへの実行指示：実装から統合検証まで完遂する

### 14.2 統合検証の必須シナリオ

ユニットテストのモックだけでは完了としない。実アプリのHTTP API、バックグラウンド処理、Blob/Table用の実Storageアダプター、安全な実ローカルプロセスを接続した統合テストをxUnitから実施する。接続先はAzuriteとし、実Azureの接続情報は必要としない。

1. 定義・カレンダーをAPIで取り込み、検証、有効化、実行登録、予定照会まで行う。
2. 予定時刻を迎えて実ローカルプロセスが開始し、標準出力・標準エラー・終了コード・履歴が取得できることを確認する。
3. 直列・並列・異常終了・後続待機・保留解除・再実行を、API応答と永続状態の両方から確認する。
4. 定義・カレンダーの変更、登録種別、一時変更の組み合わせを検証し、プレビューと実際の世代生成の整合を確認する。
5. アプリを再起動し、メモリを失っても未開始予定・登録・操作要求を復元できることを確認する。
6. 同じStorageを使うアプリを2プロセス以上起動し、通常時の稼働系が1台となること、待機系APIからの操作も反映されることを確認する。
7. 稼働系を停止・分断させ、リース切り替え、旧Epochの更新拒否、未開始予定の再開、結果不明ジョブの自動再実行禁止を確認する。第7章の保証限界も保持する。
8. 同じ操作要求の再送、ETag競合、起動・結果保存の途中障害を再現し、二重登録や履歴欠落がないことを確認する。
9. 1日1,000ジョブ相当の予定生成・処理と集中起動を検証し、遅延・メモリ・Storage要求数を測定する。
10. Releaseビルドまたは発行成果物を実際に起動し、必要な設定・資産・APIがそろっていることを最終確認する。

## 16. 起動時の定義読み込み・ハッシュ管理・時間制（追加確定要件）

本章は後から確定した起動仕様である。従来の「起動後に手動でインポート・登録する」運用を基本とせず、自動読み込み・自動確定実行登録を基本にする。APIによる管理機能は維持する。JP1互換エンジンに対するJobRunner独自の起動方針として区別する。

### 16.1 設定

設定ファイルまたは環境変数で次を指定する。名前と既定値は実装案。

| 設定キー | 環境変数例 | 内容 |
| --- | --- | --- |
| JobRunner:DefinitionSources | JobRunner__DefinitionSources__0__TargetPath 等 | 読み込み先のJP1論理パスとBlobパスの対応一覧。1件以上必須（第17章） |
| JobRunner:ManagementContainer | JobRunner__ManagementContainer | 入力定義とは別の管理用Blobコンテナー |
| JobRunner:SchedulerId | JobRunner__SchedulerId | リース・状態を共有するスケジューラーの識別子 |
| JobRunner:ScheduleTimeMode | JobRunner__ScheduleTimeMode | 24または48。初期案は24 |
| JobRunner:TimeZone | JobRunner__TimeZone | 初期案はAsia/Tokyo |
| JobRunner:ConfirmedHorizonDays | JobRunner__ConfirmedHorizonDays | 自動確定登録の先読み日数。初期案は32 |

環境変数を設定ファイルより優先する。Storage資格情報をBlobパスやログへ埋め込まない。入力Blobと管理情報の保存先を混同せず、入力ファイルを管理情報で上書きしない。

### 16.2 ハッシュと保存領域

- 入力定義の取得バイト列からSHA-256を計算する。ETagは読み取り整合性用であり、内容ハッシュの代わりにしない。
- 1件の場合も複数件の場合も、全入力の種別・正規化した読み込み先JP1論理パス・Blobパス・内容ハッシュを決定的な順序でまとめたマニフェストからDefinitionHashを計算する。読み込み先の変更、ファイル追加・削除も検出する。詳細は第17章に従う。
- 時間制・タイムゾーン等、予定の意味を変える実効設定もSettingsHashとして計算する。DefinitionHashが同じでもSettingsHashが違えば、以前の状態をそのまま再利用しない。
- 各BlobのETagを条件付き取得に使用し、全件取得後も変化がないことを確認する。複数BlobをETagだけで原子的に読むことはできないため、厳密に同じ配布版を要求する場合は不変の配布パス等で入力一式を固定する。読み取り中の変化を検知したら一式を再取得し、再試行上限で停止する。
- 管理Blobのパス例は `management/{schedulerId}/{definitionHash}/{settingsHash}/...` とする。
- `management/{schedulerId}/active.json` に現在のハッシュ、状態領域、初期化状態、登録基準時刻を記録する。
- 詳細な実行状態は引き続きTableに保存し、各行のキーにstateNamespaceを含める。ハッシュを管理パスへ使うことは、実行状態をすべてBlobだけへ移すことを意味しない。
- Tableのleader行はSchedulerId単位で共通に保つ。ハッシュごとにリースを分けると旧版と新版が同時稼働できるため、リースは定義ハッシュに依存させない。
- 同じ内容への切り戻しでも、現在のactiveと異なる版の採用は新しいactivationIdで分離する。ハッシュ配下にactivationIdを置き、過去の実行状態を無条件に復活させない。通常再起動では現在のactivationIdを再利用する。

### 16.3 起動手順

1. APIを起動する。スケジューラーは初期化完了まで実行を開始しない。
2. 共通Blobリースを取得した稼働系だけが定義の採用判断・管理状態の変更を行う。待機系が同じ定義を自動登録し直してはならない。
3. DefinitionSourcesの各対応からジョブ・スケジュール・カレンダーを全件読み、指定のJP1論理パスへ配置した統合モデルを検証し、全体ハッシュと実効設定を計算する。
4. active管理BlobとTableの有効版情報を照合する。
5. 不一致または初回なら、新しい状態領域へ保存・検証し、対象ルートジョブネットを自動で確定実行登録する。ジョブ単体やネストしたネットを独立に二重登録しない。
6. 一致なら、現在の状態領域から登録・世代・試行・保留・一時変更・未処理操作を復元する。全件を初期状態へ戻したり、全登録を作り直したりしない。
7. 過去の未開始予定を処理し、次の予定から起動可能状態にする。
8. 待機系から稼働系になった場合も同じ手順を行う。常時のBlob変更監視は今回の必須範囲に含めない。

読み取り失敗・構文エラー・未対応属性・管理状態破損は、ハッシュ変更による正常な初期化と混同しない。エラーを返し、新規起動を止める。状態が失われたときに空の状態で起動し直してはならない。

### 16.4 初期化の整合性と確定登録期間

BlobとTableは一括トランザクションにできない。初期化状態をPreparing / Ready等で管理し、登録と予定の作成を決定的なキーで再試行可能にする。Table上の有効状態を実行判断の基準とし、active管理Blobとの不一致はジャーナル等から解決する。両方が整合するまで通常起動しない。処理途中の再起動を「新しい初期化」として重複登録しない。

確定実行登録は有限の予定を作る処理として扱う。自動運用では先読み期間を設定し、期限到来前に未登録範囲だけを同じ定義スナップショットから補充する。これはJobRunner側の補充処理であり、確定済み世代の再計算や計画実行登録への置き換えを行わない。APIで解除した登録を起動や補充のたびに勝手に復活させない。

旧版の未開始予定は新規起動対象から外すが、履歴と結果不明の試行は保存する。旧版の未解決ジョブと新版の同じ業務を無条件に並行起動しない。ハッシュ領域を分けても、プロセスの二重実行防止は第7章の規則を適用する。

### 16.5 実行時間を過ぎた予定

- 新規初期化・復旧処理ごとに、時刻比較の基準となる時点を1回取得・保存する。初期化の再試行中に毎回基準を動かさない。
- 初期化時点より前の開始予定日時を持つ未開始ルート世代は起動しない。履歴に残る既存世代はスキップ理由を記録し、次回以降の予定へ進む。
- 同一ハッシュでの復旧でも、停止中に過ぎた未開始の時刻待ち世代をまとめて追い掛け実行しない。
- 基準時刻と同じ予定日時は対象に含める。通常稼働中のポーリングや負荷による数秒の遅延を「過去」として毎回スキップしない。
- 開始済みのネットの後続、保留、待ち合わせ、手動操作は別扱いとする。子ジョブの予定時刻だけを理由に履歴を消去・初期化しない。結果不明の親・先行があれば待機する。
- 旧インスタンスで実行中だったOSプロセスを復元できるとは扱わない。「続きから」は永続化された論理状態からの再開であり、Starting/Runningの結果不明処理は第7章に従う。

### 16.6 24時間制・48時間制

- スケジューラー設定で24時間制と48時間制を選択可能にする。設定はルートジョブネットのスケジュール解釈へ適用する。
- 時間制は「先読み期間24時間／48時間」ではなく、JP1の運用日・時刻の解釈に関わる設定である。
- 業務日、定義上の時刻、絶対／相対指定、基準時刻、実際の起動日時を別々に保持する。24時以上の表現をTimeOnlyへ丸めて日付情報を失わない。
- 基準時刻0:00の48時間制で、業務日11月5日の25:00を実日時11月6日01:00へ解決する例を仕様テストに入れる。日付境界・休業日評価は業務日の意味を保つ。
- 24時間制でも単純な「24:00以上はすべて不正」という推測を実装しない。基準時刻、絶対／相対指定、ネストの扱いはV12の該当仕様を確認して実装する。
- 過去予定の判定は変換後の実日時で行う。48時間制の前日業務日分でも実日時が未来なら起動対象にする。
- 時間制変更はSettingsHashの変更として扱い、新しい状態領域で登録する。旧履歴の日時を再解釈しない。

### 16.7 追加の必須テスト

- 初回起動、同一ハッシュ再起動、定義変更、カレンダーだけの変更、時間制だけの変更、旧ハッシュへの切り戻し。
- 確定登録の自動生成と将来分の補充、API解除状態の維持、初期化途中の再起動と重複防止。
- active管理Blob更新前後・Table更新前後の停止と整合回復。
- 再起動前後の完了・保留・一時変更・結果不明の保存と復元。
- 過去／同時刻／未来のルート予定、通常稼働中の軽微な遅延、開始済みネットの後続。
- 24時間制／48時間制、23:59・24:00・25:00・47:59、基準時刻0:00以外、月末・年末・休業日。
- 48時間制で業務日は前日だが実行日時は未来となる予定を誤ってスキップしないこと。
- Azuriteと2つ以上のアプリプロセスを使い、同一起動定義から登録が重複しないこと。
- 読み取り中の入力変更、Blob取得不能、管理情報欠損時に新規起動しないこと。

実装担当は本章をフェーズ2〜4および6の仕様・テストへ反映し、第14章の統合検証にも起動経路を組み込む。既存の管理API経由のインポートだけを検証して完了としない。

## 17. 複数定義の読み込み先マッピング（追加確定要件）

単一のDefinitionBlobPathと別カレンダーパス一覧を廃止し、読み込み先と入力Blobの対応一覧DefinitionSourcesへ統一する。1ファイルだけの構成も同じ形式で扱う。

ユーザー指定の「JP1/AJSジョブの読み込み先パス」は、Blob保存先やローカルディレクトリではなく、JobRunner内のJP1ユニット階層上の配置先パスとして解釈する。例: `/業務/日次 : jp1-definitions/jobs/daily.txt`。各指定パス配下に複数のファイルの定義を組み合わせて配置できるようにする。

### 17.1 設定形式案

単純な辞書では同じ配置先に複数ファイルを指定できないため、配列で表現する。

```json
{
  "JobRunner": {
    "DefinitionSources": [
      {
        "Kind": "Unit",
        "TargetPath": "/業務/日次",
        "BlobPath": "jp1-definitions/jobs/daily.txt"
      },
      {
        "Kind": "Unit",
        "TargetPath": "/業務/月次",
        "BlobPath": "jp1-definitions/jobs/monthly.txt"
      },
      {
        "Kind": "Schedule",
        "TargetPath": "/業務/日次",
        "BlobPath": "jp1-definitions/schedules/daily.txt"
      },
      {
        "Kind": "Calendar",
        "TargetPath": "/業務",
        "BlobPath": "jp1-definitions/calendars/business.txt"
      }
    ],
    "ManagementContainer": "jobrunner-management",
    "SchedulerId": "default",
    "ScheduleTimeMode": 48,
    "TimeZone": "Asia/Tokyo"
  }
}
```

- Kindは入力を処理するアダプターの選択であり、JP1の公式ファイル種別名を意味しない。
- ユニット定義ファイルにスケジュール・カレンダーが含まれる場合はUnitとしてまとめて取り込めるようにする。同じ情報を別ファイルへ分割することを強制しない。
- 別ファイルのSchedule/Calendarは、実際のJP1 V12の出力形式・対象指定方法を確認してアダプターを実装する。未知の形式を推測で読み取ったり、独自JSONをJP1形式として扱ったりしない。
- BlobPathはコンテナー名とBlob名を含む明示的なファイルパスとし、大文字小文字を保持する。初版はBlobプレフィックスの無差別な再帰走査やワイルドカードを必須にしない。
- 環境変数例: `JobRunner__DefinitionSources__0__Kind=Unit`、`JobRunner__DefinitionSources__0__TargetPath=/業務/日次`、`JobRunner__DefinitionSources__0__BlobPath=jp1-definitions/jobs/daily.txt`。
- 環境変数による部分上書き後の実効一覧を検証する。設定ファイルの配列末尾が残る等の設定マージを考慮し、実際に読み込む一覧を秘密情報なしで確認できるようにする。

### 17.2 配置・参照の規則

- UnitのTargetPathは、入力ファイル最上位のユニットを配置する親グループとする。例として、最上位ユニット名が日次ネットでTargetPathが/業務/日次なら、配置結果は/業務/日次/日次ネットとなる。
- 配置先の親グループが存在しない場合はコンテナーとして作成する。ただし既存ジョブ等とパスが衝突する場合はエラーにする。
- 入力に絶対パスがある場合は単純に文字列連結しない。JP1 V12の定義形式を確認して入力側の基点を解決し、配置先への変換を行う。基点を一意に解決できない場合はファイル名・行番号とともに拒否する。
- 相対参照は各定義の配置後の基点から解決する。外部への絶対参照は勝手に書き換えず、統合モデル上の参照先を検証する。元パスと配置後パスの対応を診断情報へ残す。
- ScheduleのTargetPathは対象指定を解決する基点とする。配下の全ジョブへ無条件に同じスケジュールを適用しない。ファイル内の対象ユニット指定を解決し、存在しない・曖昧な対象は拒否する。
- CalendarのTargetPathはカレンダー適用・配置の基点とし、実形式に従ってグループ属性や参照を解決する。全体に適用したい場合は/を明示する。
- ジョブ・スケジュール・カレンダーをすべて解析した後で、ユニット間接続、カレンダー継承、参照先、循環、実行属性を一括検証する。設定の配列順に依存して参照可否が変化しないようにする。
- 同じ配置先を複数ファイルが使うことは許可する。ただし同一ユニット完全名の重複、同じ属性への二重定義、既存の埋め込みスケジュールと別ファイルによる競合は、後勝ち上書きにせずエラーとする。
- まったく同一のKind・TargetPath・BlobPathの重複指定も設定エラーにする。1つのBlobを異なるTargetPathへ読み込む指定は許可し、それぞれ独立した配置として扱う。
- TargetPathの区切り・末尾等はJP1パス規則に基づき正規化する。ユニット名の大文字小文字やUnicodeを無断で同一化しない。

### 17.3 ハッシュ・有効化・再開

- 各入力についてKind、TargetPath、BlobPath、SHA-256、取得ETag等をマニフェストへ記録する。ETagは取得証跡として保持し、内容が同じならETagだけの変更でDefinitionHashを変えない。
- 定義形式上順序に意味のない対応一覧は安定ソートし、境界の明確なシリアライズ形式で全体ハッシュを計算する。設定行の並べ替えだけで再登録しない。
- 入力内容が同じでも配置先パス・種別・ファイル一覧が変わった場合は、新しい定義として扱う。
- 管理情報は全入力をまとめたDefinitionHash配下へ分離する。各ファイルが独立にactiveを更新する方式にはしない。
- 全入力の取得・解析・参照検証に成功してから有効化し、統合後の対象ルートジョブネットを一度ずつ確定実行登録する。
- 1件でも欠落・構文エラー・参照不整合があれば、部分的な定義だけで新規実行を開始しない。前の履歴や管理情報は削除しない。
- 全体ハッシュとSettingsHashが一致する場合は、その状態領域から一括で再開する。ファイル数だけ同じ登録を重複作成しない。
- 複数ファイルの更新途中を配布済みと誤認しないため、起動前に更新を完了させる運用を基本とする。同じ配布版を厳密に保証する構成では、変更されないリリース別パスと対応一覧を一組で切り替える。

### 17.4 追加の受入・統合テスト

- 複数のUnit入力を別の親グループへ配置し、完全名と実行対象が正しい。
- 同一親グループへの複数ファイル、同じBlobの異なる配置先への読み込み。
- 別ファイル間の依存関係、Scheduleの対象解決、Calendarの継承・参照。
- 重複ユニット・属性競合・未解決参照・入力欠落を有効化前に拒否する。
- 対応一覧の順序変更ではハッシュ・登録を維持し、配置先変更・追加・削除・カレンダーのみの変更では新しい領域へ切り替わる。
- 全体が同一の場合は保留・一時変更・完了履歴を保ったまま再開する。
- 複数Blobを更新中の起動と初期化途中の停止でも、部分登録や重複登録を起こさない。
- Azuriteに例示構成の複数Blobを配置し、環境変数だけの設定でも実API・実ローカルプロセスを含む起動から実行まで検証する。
