# JobRunner の実行と復旧

## 目的

JP1 V12 の定義を取り込み、ローカルジョブを永続化された世代に従って実行する。確認済み要件と最終受入条件の正本は [実装計画](../../implementation-plan.md) とする。

## 仕様

- 入力は明示された文字コードのBlob。全入力の配置・検証を完了してから一括採用する。未知の実行属性は拒否する。
- UTC、業務日、定義時刻を別々に保存する。登録の基準日は登録時に固定する。
- リースはSchedulerId単位。状態更新には所有者・Epochの照合とleader行のETagを含むTableトランザクションを使う。
- 再起動では完了・保留・操作を保存状態から復元する。過去の未開始ルート世代はスキップする。
- Starting/Runningの結果不明は自動再実行しない。手動解決には試行ID、期待状態、理由が必要。
- APIは認証なし。JP1の未確認APIを独自の形式で代用しない。

## 受入条件

計画第13・16・17章の全条件を追跡し、検証結果に確認済み・未達・未検証を記録する。特に以下を独立したテストで確認する。

| 条件・操作 | 期待する結果 |
| --- | --- |
| 入力の並べ替え、ETagだけの変更 | 定義ハッシュと登録を維持 |
| 配置先、本文、実効時間制の変更 | 新activationへ分離 |
| 同一IDのAPI要求を再送 | 同内容は同じ操作、異なる内容は409 |
| 古いleaderで状態を書き込む | 条件付きトランザクションが拒否 |
| 予定の過去・同時刻・未来 | 復旧時のみ過去の未開始予定を除外 |
| 未対応属性、重複、循環、欠落 | 部分的な定義で開始しない |

## 未確定

実JP1環境での比較、別ファイルSchedule/Calendarの実出力、保証対象Windows環境、保存期間初期値は未確定。仕様調査・実装状況は互換表で区別する。

## 現在の実装範囲

実装計画の最終目標は変更しません。現時点では中核の定義・永続化・起動・ローカル実行・復旧と独自管理APIを実装しています。計画登録やJP1 HTTP APIの未対応操作などの未達は [検証結果](../../verification-results.md) と [互換表](../../compatibility-v12.md) に明記しています。未実装の操作を成功扱いする代替実装は設けません。

## 続きの実装：終了状態・履歴保持

- 異常終了した子を持つネットは、実行中の子や開始可能な独立後続がなくなったらFailedへ移る。Unknownを正常・異常と推測しない。
- 末端ジョブを再実行すると、新しい試行を作り、Failedの祖先ネットをRunningへ戻す。完了した他のジョブは再実行しない。
- HistoryArchiveAfterDays、LogRetentionDays、OperationArchiveAfterDaysを任意の正整数で指定する。未指定は自動処理しない。保持期間の既定日数は未確定のため設定しない。
- 完了したルート一式の履歴を不変Blobへ保存・照合した後にTableの詳細を削除する。ルートには世代IDと退避先の墓標を残し、再生成・再実行を防ぐ。
- 退避途中はArchiving、完了はArchivedで表す。途中停止後も同じBlobとETagで続行する。100操作制限に合わせて分割する。
- 実行中、保留、未開始、結果不明のあるルートは退避しない。未開始の後続が残るFailedネットも退避しない。
- 完了操作は原要求をBlobへ退避し、同じIdの再送を識別するハッシュ・結果はTableへ残す。保持期限後の再送も二重操作を起こさない。
- ログは既知の終了試行のみ期限削除する。Unknownのログは保持する。履歴退避とログ削除は別設定で扱う。

受入テストは、期限前後、Unknown除外、Blob保存不能時の非削除、退避途中からの再開、退避後の要求再送、終了コード・後続待機・再実行による新試行と祖先状態を確認する。残りのJP1互換・スケジュール機能は引き続き実装対象とする。

## JP1 HTTP契約の追加

3021-3-D28-20の6.5.2、7.1.7、7.1.9、7.4.8に基づき、まず即時実行登録と保留変更を追加する。URL・parametersラッパー・execID・SET/RELEASE・同期200を維持し、独自202で置き換えない。認証は計画どおり対象外。

- managerは設定Jp1ManagerName、serviceNameはSchedulerIdに一致させる。別ホストへのリモート処理は行わない。
- 起動条件や非空macroなど未実装の指定は400で拒否し、実行しない。
- execIDは公式の書式に従う独自の単調採番とし、JP1の内部採番順序を保証しない。leader行・カウンター・ルート世代を同一トランザクションに含める。
- 独自任意ヘッダーX-JobRunner-Request-Idで再送を識別できる。HTTP受付後30秒で結果が確認できなければ500と操作IDを返し、操作自体を取り消さない。
- エラーは公式のerrorSource/message/messageID/application/extensions形状を使用する。確認できた必須引数不足以外のメッセージIDはJobRunner固有と明示し、完全なエラーメッセージ互換は宣言しない。
- 受入は実HTTPで、符号化ユニットパス、holding指定、同期応答、空ボディ、無効引数の非実行、同一ID再送を検証する。

## ユニットヘッダーと状態復元

5.1.1の `unit=名称,許可モード,所有者,資源グループ;` を保持する。許可モードは4桁の8進数、資源グループは英数字・下線の1〜63文字とする。所有者実行を指定するモードでは、所有者をLocalUsersで現在のOSユーザーへ明示対応させる。OSユーザー切り替えとJP1認証は行わない。入力絶対名は引き続き未対応として拒否する。

ヘッダーの省略時は追加フィールドを不変定義JSONへ出力せず、LocalUsers空配列時は従来の設定ハッシュを維持する。受入はDefinitionTestsでメタデータ保持・未対応所有者拒否・不正モード拒否を確認する。

ExecutionControlTestsで、一時変更後もOriginalDueを保持し、同じ入力の再起動後も登録解除・保留・変更予定を維持することを確認する。StorageTestsではUTCの前進・巻き戻りにかかわらず単調時計の期限で旧所有者を失効させる。ScaleTestsでは実Storageと1000末端プロセスで二重実行がないことを検査し、要求数・開始遅延・サンプル時点の管理ヒープ使用量を記録する。

操作モデルの追加nullable項目は未指定時にJSONへ出力せず、旧版で受け付けた独自API要求のハッシュを維持する。RetentionTestsで旧形式JSONとの一致と明示holding指定による識別を確認する。
