# 定義編集の性能確認（2026-11-06）

比較元はPR #7の`ff84f69b6578249c6abbb53366330609374b0b0b`。改善後はこの記録を含むコミットの実装。測定中のGit HEADは比較元のままで、変更は作業ツリーに適用した。CIの合否と性能測定は区別する。

## 条件と再現

Linux、.NET 10.0.14、Releaseビルド。実行時の`Environment.ProcessorCount`は4、Pythonの`os.cpu_count()`は5。ブラウザーは同じ環境のHeadlessChrome 155.0.0.0・1440×900・ja-JP・Asia/Tokyo、Viteのproduction previewを使用。測定は順番に行い、ビルドや他の試験と重ねない。共有クラウド環境での少数サンプルであり、SLAや統計的な保証ではない。

- 純粋処理: `tools/JobRunner.EditorBenchmarks`。各操作を1回ウォームアップし、GC後に3回計測した中央値。文字列の一箇所のコマンド変更を検証する。出力は原文の再生成・検証・バイト化までで、HTTPやZIP圧縮を含まない。入力は独立した2ノード接続を持つネット群。長い依存チェーンや大量のファイルを代表しない。
- 時間はStopwatch、割当量は当該スレッドの累積割当。`managedBytes`、`workingSetBytes`は処理後の観測値で、ピークではない。GiB単位の割当が同時に常駐するという意味ではない。
- 各ケースを独立プロセスで実行し、編集45秒・予定10秒でそのプロセスだけを終了。比較前の9,000ジョブは45秒で打ち切られ、出力は2サンプルのみ。他の編集操作は3サンプル。予定の大規模3ケースはウォームアップ中に10秒で終了し、操作単位の計測値はない。
- ブラウザー: 200×1、1,000×1、200×25ネットの3ケース。HTTPの読込・検証・出力・試算を各3回、その後ローカル読込、ジョブ選択、コマンド変更と自動保存を3回測定。編集時間はPlaywright操作と2フレーム待機を含む。保存完了は新しいIndexedDB readwriteトランザクションの完了と保存済み表示の両方で待つ。
- ブラウザーのHTTP試算は予定なし(`sd=0,ud`)で、下書きの検証を含む経路の測定。実際の予定計算は別の純粋処理ケースで測定した。
- ブラウザーのJSヒープは強制GCなしの処理後観測。DOMノード数とlong taskも記録するが、保持メモリやピークとして扱わない。最初のブラウザー試行はフォームを探す測定側locatorが一致せず中止した。textboxのroleによる待機へ修正後、比較前・比較後とも同じ測定コードで完走した。

```sh
# PATH等に.NET SDKを設定済みでリポジトリルートから実行
# 既存サービスや業務用Storageを使わず、ローカルの純粋処理のみを測定
dotnet build tools/JobRunner.EditorBenchmarks -c Release
python3 scripts/benchmark-editor.py measurement /tmp/editor-performance

# ブラウザー測定。バックエンドReleaseも先にビルドする
cd src/JobRunner/clientapp
npm ci
npm run build
# ChromiumをPlaywrightで導入するかPLAYWRIGHT_CHROMIUM_EXECUTABLEを指定
EDITOR_BENCH_PRODUCTION=1 EDITOR_BENCH_LABEL=measurement \
EDITOR_BENCH_OUTPUT=/tmp/editor-browser-performance.jsonl npm run benchmark:editor
```

ブラウザー測定は既存e2e起動器の専用Azurite（11300〜11302）、API（5181）、Vite（5174）と一時データを使用する。既存の下書きや業務データを変更しない。SDK探索に必要なら`DOTNET_HOST_PATH`を設定する。比較元の測定にはこのコミットの測定用ファイルだけを持ち込み、アプリ本体を変更しない。通常CIのPlaywright対象に`.perf.ts`は含めず、性能の絶対時間で合否を判定しない。

## 改善内容

1. 接続検証で子ジョブごとに全`ar`を正規表現解析していた箇所を、ネットごとの一度の解析と先行/条件接続の索引へ変更。元の検証順、重複接続の件数、拒否理由を維持する。
2. 編集投影の`el`をネットごとに索引化。同名の先頭値が不正でも後続値へフォールバックしない。改名時の親別ノード探索も一度だけ索引化する。原文置換・文字コード・ファイル対応は変更しない。
3. カレンダーの稼働日・業務月を1回の計算中だけ再利用。稼働/休業日サイクルの経過日数は累積個数の差で計算し、古い基準日からの走査を候補日ごとに繰り返さない。登録・補充の保存手順やID、予定の重複優先順は変更しない。
4. 結果上限より前の予定計算にも、下書き試算専用の5秒の協調的な中断とHTTP要求の取消を導入。期間/ルール数を減らす診断を返し、部分結果は返さない。原文読込・編集反映・検証の時間はこの5秒に含まない。登録・補充にはこの期限を適用しない。
5. Reactの描画ごとに繰り返していた下書き比較用JSON、パス/実行対象一覧、作成用基点を入力変更時だけ再計算。保存キュー、IndexedDBの世代比較、競合時の停止、古い応答の識別は維持する。

## 限界と残る改善余地

- SVGとユニット/属性の選択肢は全件描画のまま。1ネット1,000ジョブで実DOMは17,480ノードあり、描画・編集・保存にはまだ数百ms〜1秒を要する。仮想化、操作対象の絞り込み、キーボード/アクセシビリティを保つ描画分割は今回実装していない。
- 初回読込の5,000ジョブは一度の測定で悪化した。単一サンプルを隠さず記録し、追加測定の結果を下記へ追記する。長いmain-thread taskとGC/非同期保存の影響を分離した性能保証はできない。
- 自動保存は基点と下書き全体を世代比較付きで保存する。差分保存、履歴の圧縮、保存遅延の導入は、復旧・複数タブ競合・応答喪失の契約が変わり得るため見送った。
- 予定の結果集約は全ルールの候補生成後であり、144ルールの例でも累積約190〜205MiBを割り当てる。途中で2,000件に切り詰めると日時順・重複ルールの優先が変わるため、その最適化は行わない。5秒は日単位・稼働日計数単位で確認する協調的な中断であり、プロセスの厳密な実時間/メモリ上限ではない。
- 多数同時HTTP要求の総CPU/メモリ制限、最大32ファイル/8MiB、深さ64の全組合せ、長い依存チェーン、ブラウザーの容量不足/低メモリ端末の負荷試験は未実施。入力上限は負荷試験済みの規模を保証するものではない。
- 実JP1、Windows、実Azure、Chromium以外は今回未検証。JP1契約、カレンダー境界、CP932別符号の拒否など既存の制限は変えない。

処理後のプロセスRSS観測範囲は、1,000ジョブで208〜222MiB → 100〜161MiB、9,000ジョブで256〜310MiB → 218〜343MiBだった。大規模ケースの最大観測RSSは増えており、累積割当の削減を常駐メモリ削減と同一視しない。索引・GCヒープ・結果の保持を含む観測で、全区間のピークRSSは採取していない。

## 初回描画の追加確認

5,000ジョブの初回描画悪化を調べるため、比較元を別ディレクトリへ取り出してRelease/productionビルドし、同じ測定器で比較元3回、その後改善後3回を独立したブラウザーコンテキストで実行した。他のビルド・試験は重ねていない。

|操作|比較元3回の中央値|改善後3回の中央値|
|---|---:|---:|
|初回読込→描画|2125ms|1773ms|
|編集→描画|505ms|405ms|
|編集→保存完了|706ms|600ms|

初回描画は比較元2309 / 2125 / 1918ms、改善後1773 / 1894 / 1699ms。最初の改善後5168msは追加3回では再現しなかったが、元の記録を削除しない。単発で長いmain-thread taskと保存トランザクションが観測されており、GC・OS負荷・描画/保存待ちの寄与までは確定できない。平均的な短縮を全操作の最悪時間保証とはしない。

## 計算中断の実負荷確認

有効な日付休業属性`cl=1994/1/1`を50,000回含む、600,082バイトの単一Unit原文（入力2MiB以内）を使用。1994年基準・1ルール・31日を試算し、外側は専用プロセスを30秒で終了する条件にした。1回のウォームアップと3回の測定すべてで、プロセス強制終了より先に5秒の計算中断診断を返した。通常の時間依存CIテストには含めない。

3回の計算時間は5009ms / 5009ms / 5032ms。全体は20.7秒、終了コード0、外側の打切りなし。部分結果は返さない。大きいカレンダーでは期間やルール数を減らすだけでは速くならない場合もあり、カレンダー定義自体の見直しが必要になる。

この負荷では中断までに約681〜1,189MiBの累積割当が発生した。時間の中断だけでメモリ割当や同時要求の総負荷を制限できるわけではない。カレンダー属性の事前索引化は今後の改善候補として残す。

この`calendar-load`ケースは中断確認用に後から追加したため、比較元の時間測定は行っていない。CLIドライバーではこのケースだけ30秒の外側制限を使用する。
